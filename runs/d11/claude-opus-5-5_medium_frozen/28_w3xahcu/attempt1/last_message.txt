I wrote the tests and the suite passes, but `is_prime` in solution.py is wrong for most inputs. The 11 tests that hit the bug are marked as expected failures rather than counted as passes. Running `python -m pytest test_solution.py -q -rx` in <work>\work gives 16 passed, 11 xfailed. solution.py was not modified.

**The bug:** the loop is `for k in range(1, n - 1)`. It starts at k=1, and every number divides by 1, so:
- every n >= 3 returns False, including primes like 3, 11, 101 and 13441;
- 1 returns True, because the loop never runs.

Running the function confirmed this. Most of the examples in its own docstring fail (only `is_prime(6)` and `is_prime(4)` come out right). The fix is in solution.py, not the tests: start the loop at 2, i.e. `if n < 2: return False` and `for k in range(2, n)`, or better `range(2, int(n**0.5) + 1)`.

**What the tests cover** (all written against the docstring, not against what the code currently does):
- **Passing (16):** zero and negative numbers are not prime, 2 is prime, composites (4, 6, 8, 9, 15, 25, 49, 100, 13440) are not prime, and the result is a real bool.
- **Expected failures (11):** 1 is not prime, primes (3, 5, 7, 11, 13, 61, 97, 101, 13441) are prime, and the docstring examples hold.

The expected-failure markers are strict. Once solution.py is fixed, those tests start passing and pytest fails the run, which is the signal to delete the `@BUG` markers. The alternative was tests that assert the buggy output, such as `is_prime(11) is False`; that would have looked green but locked in the bug.
